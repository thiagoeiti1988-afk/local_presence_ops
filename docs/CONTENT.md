# Content generation

`packages/content` defines the `ContentProvider` interface
(`draftReviewReply`, `draftPost`, `summarizeReviews`) and three
implementations. Nothing generated by any of them is ever auto-published —
see [REVIEWS.md](REVIEWS.md) for the review-reply approval gate; `LocalPost`
has its own `draft -> approved -> published` status that the UI/app must
move through explicitly.

## MockContentProvider

Fixed, non-branching output — used in tests. If you see `[mock]` text
anywhere outside a test, the wrong provider is wired in.

## RuleBasedContentProvider (default)

Template-based: branches on `classifyReview`'s sentiment for reply drafts,
and on post `type` for posts. Deterministic given the same input, no
external call, no API key required. This is what the demo scenario
(`scripts/demo.ts`, `apps/web/lib/demo-repository.ts`) uses.

## OpenAIContentProvider (optional)

Only usable when `OPENAI_API_KEY` is set — its constructor throws otherwise,
by design, so a missing key fails loudly at construction rather than at the
first generation call. Talks to the OpenAI Chat Completions REST API
directly via `fetch` (no SDK dependency added, to keep the package's own
dependency footprint at zero beyond what it already needs). Swapping to a
different LLM vendor means writing one more class next to this one — nothing
elsewhere in the codebase references `OpenAIContentProvider` directly.

## Why not call an LLM for audit scoring

`packages/audit`'s scoring is deterministic on purpose (see
[AUDIT_SCORE.md](AUDIT_SCORE.md)) — content generation and scoring are
different concerns with different reliability requirements, and mixing them
would make the score non-reproducible.
